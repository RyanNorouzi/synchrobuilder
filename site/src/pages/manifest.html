The manifest

synchrobuilder.json describes what a project needs to run. This page states the format as proposed in ADR-004, which awaits approval. draft v1

StatusDraft v1, from ADR-004 (status: Proposed, dated 2026-09-18). The normative docs/manifest-spec.md arrives in Phase 4, together with the reader and writer. No code reads or writes this file yet.

Purpose

init writes the manifest, setup and doctor read it on another machine, and ci turns it into a GitHub Actions matrix. The brief requires the format to be simple, versioned, documented, and not tied to Claude so other coding agents can adopt it. The plugin has no runtime dependencies, so the format must be parseable with the Node standard library.

Principles

  • JSON only. One file, synchrobuilder.json, at the repository root. UTF-8, LF, two-space indent when the plugin writes it. No comments in the file; explanations go in hint and description fields, which the tooling shows to humans.
  • Integer version. A top-level "version": 1. Readers reject a higher major version with a clear message and accept lower ones with defaults. Additive changes do not bump the version; removals and semantic changes do.
  • Exact runtime versions. runtimes[].version is an exact version string. Setup installs or verifies exactly that version; doctor reports the difference. Ranges are not allowed in v1, because "works on my machine" is the bug being removed. A semver range may be added as allowedRange in v2 without a version bump.
  • Env var names and descriptions only. A value field is not part of the schema, and the writer refuses to serialize one.
  • Commands are plain argument strings without shell syntax. The runner splits them with a small, documented tokenizer (quotes and backslash escapes only) and spawns the program directly. These tokens are rejected with a message pointing at the audit rule that explains why: &&, |, $VAR, >. A project that needs a shell pipeline puts it in a Node script and calls that.
  • Per-OS overrides are limited. os.windows, os.macos and os.linux may override commands and runtimes only. Nothing else is per-OS, on purpose.
  • Extensions carry an x- prefix. Unknown top-level keys are allowed only with that prefix, which keeps the door open for other tools without silently accepting typos.
  • Nothing mentions Claude. The file never names Claude, hooks or the plugin.

Example

The skeleton from ADR-004, copied without changes. The project, versions and service in it are illustrative.

skeleton · ADR-004 · no code reads or writes it yet
{
  "$schema": "https://synchrobuilder.dev/schema/manifest-v1.json",
  "version": 1,
  "name": "acme-portal",
  "runtimes": [
    { "name": "node", "version": "24.16.0", "detect": "node --version" }
  ],
  "packageManager": { "name": "pnpm", "version": "10.22.0" },
  "services": [
    { "name": "postgres", "version": "16", "port": 5432,
      "hint": "Any Postgres 16 reachable at DATABASE_URL" }
  ],
  "env": [
    { "name": "DATABASE_URL", "description": "Postgres connection string", "required": true },
    { "name": "SESSION_SECRET", "description": "Random 32+ character string", "required": true }
  ],
  "commands": {
    "install": "pnpm install --frozen-lockfile",
    "migrate": "pnpm prisma migrate deploy",
    "seed": "pnpm run seed",
    "start": "pnpm run dev",
    "test": "pnpm test"
  },
  "healthCheck": {
    "type": "http",
    "url": "http://localhost:3000/health",
    "timeoutSeconds": 60,
    "expectStatus": 200
  },
  "os": {
    "windows": { "commands": { "start": "pnpm run dev:win" } }
  }
}

The $schema URL in this example is a placeholder. See the last section on this page.

Fields

ADR-004 fixes the shape and a few rules. Where it does not say whether a field is required, the spec will.

FieldTypeRequiredWhat ADR-004 says
$schemastring (URL)to be fixed in the specPoints at a JSON schema served from the website so other tools can validate against it. The URL is a placeholder today.
versionintegerto be fixed in the spec1 for this draft. Readers reject a higher version with a clear message and accept lower ones with defaults.
namestringto be fixed in the specThe project name. Only its presence in the example is agreed.
runtimes[]array of { name, version, detect }to be fixed in the specversion is an exact version string; ranges are not allowed in v1. detect is a command string, node --version in the example; its use is to be fixed in the spec.
packageManager{ name, version }to be fixed in the specName and version of the package manager, pnpm 10.22.0 in the example. ADR-004 requires exact versions for runtimes[] only; whether the same rule applies here is to be fixed in the spec.
services[]array of { name, version, port, hint }to be fixed in the specA service the project needs, such as a database. hint is human-facing text; redaction runs on it before anything is shared (ADR-005).
env[]array of { name, description, required }to be fixed in the specNames and descriptions only. A value field is not part of the schema and the writer refuses to serialize one. Redaction runs on description before anything is shared.
commandsobject with install, migrate, seed, start, testto be fixed in the specEach value is a plain argument string without shell syntax. &&, |, $VAR and > are rejected.
healthCheck{ type, url, timeoutSeconds, expectStatus } in the exampleto be fixed in the spectype is http (GET a URL, expect a status) or command (spawn a program, expect exit 0). Both have a timeout. ADR-004 does not name the field that holds the program for the command type; the spec will.
os.windows, os.macos, os.linuxobject with commands and/or runtimesoptional (ADR-004: "may override")May override commands and runtimes only. Nothing else is per-OS.
x-*anyoptional (ADR-004: "allowed")The only unknown top-level keys a reader accepts. Any other unknown top-level key is not accepted silently, which catches typos.

Field names, nesting and the rules in the last column are quoted or paraphrased from ADR-004. Types are read off the example; the spec will state them formally.

How Synchrobuilder uses it

Four planned Phase 4 commands. None exists yet; see the Commands page.

Writes it

  • /synchrobuilder:init inspects the project and writes synchrobuilder.json: runtimes with exact versions, the package manager, services such as a database, env var names with descriptions (never values), the install, migrate, seed and start commands, and a health check.
  • Exact versions mean the manifest changes whenever the team upgrades Node. /synchrobuilder:init --refresh re-detects and shows a diff.

Reads it

  • /synchrobuilder:setup compares the manifest to what is installed, shows a step-by-step plan for this OS, asks before each install, then runs the health check. It uses the OS's native package manager (winget, Homebrew, apt), pins exact versions and never elevates silently.
  • /synchrobuilder:doctor records a fingerprint of a working machine, or explains why this machine differs from the manifest, most likely cause first.
  • /synchrobuilder:ci generates a GitHub Actions workflow that installs, builds, tests and health-checks the project on ubuntu, macos and windows, plus a README badge. The badge only says "verified" when that workflow passes.

Because the schema forbids values for env vars, an audit rule for "secret in manifest" is structurally unnecessary. Redaction still runs on hint and description text before anything is shared (ADR-005). The Phase 4 acceptance criteria in PLAN.md are: the demo repo's generated workflow passes on all three operating systems; setup on a clean CI runner reaches a passing health check for the demo repo; and doctor on a runner missing Postgres reports it first, with the OS-specific fix.

Commands on Windows, without a shell

The runner never hands a command string to a shell. On Windows that needs one extra step.

On Windows, npm, pnpm and yarn are installed as .cmd shims, and those cannot be spawned directly without a shell. The Claude Code hooks reference states the same limit for exec-form hooks: the .cmd and .bat shims that tools install "are not executables and can't be spawned without a shell", and the recommended fix is to invoke the underlying script with node, because node.exe is a real binary.

The planned runner follows that technique. It resolves the package manager to its JavaScript entry point and runs it with node: for npm, <node prefix>/node_modules/npm/bin/npm-cli.js; for Corepack-managed pnpm and yarn, the Corepack shim's JavaScript entry. If resolution fails, setup says so and offers to open a shell command for you to run yourself, rather than running a shell silently.

UnverifiedADR-004 records that this entry-point resolution has not been run on a Windows machine. It is a Phase 4 acceptance test on the Windows CI runner, which does not exist yet. Everything verified so far ran on macOS with Claude Code 2.1.218 on 2026-09-18 and is listed in docs/research/experiments.md.

Schema URL

A placeholder until the website domain is decided.

The example points $schema at https://synchrobuilder.dev/schema/manifest-v1.json. That address is a placeholder: no schema file exists, nothing is served there, and the website domain is one of the open questions in PLAN.md. ADR-004 plans for the schema to be served from the website in Phase 7 so other tools can validate against it. Until then, ADR-004 in the repository is the source for everything on this page.
