What v1 will do about seats

Planned: one isolated module, one friendly note, nothing disabled.

v1 has no payments, no license enforcement and no accounts. The plan gives the plugin no way to know who is paying and no server to ask.

The only seat-related behaviour is a count. The plan for /synchrobuilder:status is to count distinct active handles over the last 30 days, using the local team state the plugin is designed to keep on your machine anyway. A handle is the identity Synchrobuilder derives from your git email through the committed .synchrobuilder/team.json file. When that count is more than three, status would show a friendly, non-blocking note once a week that points at this page. That is the whole mechanism.

The logic is planned as a single isolated file, lib/seats.mjs, so you can read it in one sitting and confirm it does nothing else. PLAN.md lists it under Phase 6, with this acceptance test: the notice appears once per week only when more than three handles were active in 30 days.

What the count does

  • Counts distinct handles active in the last 30 days.
  • Shows one note per week in /synchrobuilder:status when the count is above three.
  • Points at this page.
  • Lives in lib/seats.mjs and nowhere else.

What it never does

  • Disable a feature, a command or a hook.
  • Block a prompt, an edit or a sync.
  • Contact a server or send the count anywhere.
  • Ask for a card, a key or a login.

Every claim in this section is planned behaviour from PLAN.md (Phase 6) and docs/commands.md (the status entry). None of it is written or tested yet.

Questions

Short answers with the design document they come from. Every answer describes the plan; none of it is built.

Do I need an account?

No. There is no sign-up, no password and no token. Your identity is a handle: your git config user.email is matched against the .synchrobuilder/team.json file committed in the repo. If your email is not listed you get a provisional handle derived from it and keep working. /synchrobuilder:iam overrides the handle for one checkout on one machine. See How it works and ADR-002.

Is there a server?

No. Team state travels over the git remote you already have. Each developer and device publishes one small ref of its own; nothing is merged and nothing is hosted. A team that can push to its remote can use it. See ADR-001 and the Security page.

What counts as a seat?

Per the plan, a seat is a distinct handle that was active in the last 30 days. The plan gives the plugin nothing else to count: a handle is the identity (ADR-002). The details may change while the plugin is built, and they will be documented on this page before any billing exists.

Can I self-host?

There is nothing to host. The plugin is designed to run on each developer's laptop and talk to your git remote. A hosted hub is out of scope for v1; ADR-001 keeps the transport interface open for one later, but nothing about that is built or priced.

Where do I install it?

Nowhere yet. The install commands on the Install page are the planned ones, and the repository OWNER/REPO is a placeholder until the code is public.
