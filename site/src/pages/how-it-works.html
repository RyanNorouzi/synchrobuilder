The transport

One small ref per developer and device on the git remote you already have. Nothing to host.

StatusEverything on this page is a design, recorded in ADR-001, ADR-003 and ADR-005 in the repository. Phase 0 (research and plan) is complete. No plugin code exists yet. Where a step was verified by a recorded run, the page says so and names the experiment.

In the planned design, each developer and device publishes exactly one ref on the team's remote: refs/synchrobuilder/v1/<handle>/<device>. The handle is a short name matched from your git email through the committed team file (ADR-002); the device id is a random 8-hex value made once per machine and stored locally, never the hostname. The tip of that ref is always a parentless snapshot commit whose tree holds only that writer's files: presence, claims, board entries, contract alerts, messages, handoffs and a small manifest that readers check against the ref name.

There are no merges, ever. The writer builds each snapshot with git plumbing (hash-object, mktree, commit-tree) and pushes with --force-with-lease, never bare --force. It never reads anyone else's state before writing, so nothing a teammate pushes can stop you publishing. Every commit message starts with [skip ci]. A custom ref namespace stays out of branch lists, and the design expects it to sit outside branch rulesets. GitHub's reference API documentation accepts any name that starts with refs/ and has two slashes; no hosted provider has been tested yet, and ruleset behaviour is on the Phase 5 list to verify.

The planned fallback ladder: if a host rejects the custom namespace, the plugin falls back to branches under refs/heads/synchrobuilder/v1/ in fast-forward append mode, with [skip ci] and -o ci.skip on every push. If that is rejected too, it goes read-only (fetch only) or local-only and records the server's reason so the digest can say why publishing is blocked.

All git work happens in a hidden bare repository under ~/.synchrobuilder/remotes/<sha256 of the normalized remote URL>/state.git, run by a detached Node worker. Your own .git is never written to, and your branches and working tree are never touched. The worker fetches every 30 seconds plus up to 15 seconds of jitter, and pushes only when your state changed or 60 seconds passed. Important events (a claim, a release, a message, a board change, a handoff, a closed session) trigger a sync tick within about a second. Credentials come from your global git configuration only; git is spawned as an argument list with no shell and with per-call timeouts.

Hooks never run git and never open a socket. They find the checkout by reading .git/config and the gitdir and commondir files, then read snapshot.json from the plugin's own state directory under ~/.synchrobuilder. Every hook runs inside one try/catch; on any error it writes one line to a local log, prints nothing and exits 0. It never exits 2, so it can never block you.

What the hooks tell Claude depends on how fresh the snapshot is. Under 5 minutes old: full policy. Between 5 and 15 minutes: an ask collision setting degrades to warn. Over 15 minutes: warn only, with an "as of HH:MMZ" stamp. Over 24 hours: only the session digest mentions that sync is stale. Stale data never blocks and never asks.

Verified so far, on macOS with git 2.39.5 (experiments E5 and E8 in docs/research/experiments.md): worktree-less snapshot commits, push and force-push of a custom ref, a second clone and a shallow clone fetching the namespace with their own branches untouched, and a hook-spawned worker outliving the hook. Not verified: any hosted git provider, Windows, Linux, and the fallback ladder against a real host.

What leaves your machine

A short, fixed list. Everything on it passes secret redaction first.

Leaves, after secret redaction

  • Your handle (never your email)
  • A random 8-hex device id (never your hostname)
  • Your branch name
  • A task summary of at most 140 characters, derived locally
  • Repo-relative file paths you claim or edit
  • Short messages of at most 400 characters
  • Structured handoff notes built from local session events
  • Board entries
  • Claims with timestamps
  • Contract change alerts: repo-relative paths and exported symbol names

Never leaves

  • Your prompts
  • Transcripts
  • File contents
  • Diffs
  • Environment variable values (the manifest records names only)
  • Your email address (the commit author is <handle>@synchrobuilder.invalid by default; using your real email is an explicit opt-in for hosts with author rules, per ADR-001)
  • Claude's replies

Contract change alerts carry repo-relative paths and exported symbol names only. This is a deliberate difference from claude-code-relay, which sends the code-stripped prose of Claude's replies and contract-file diff hunks; Synchrobuilder sends neither. Handoffs are built by heuristics from the session's own event stream, never from transcripts and never by an extra model call.

Anyone who can fetch the repository can read this state, including everyone in the world for a public repository. The planned setup screen states this before anything is published, and the planned doctor command warns when the remote is public. The redaction module is planned to be the same one that sanitizes incoming teammate text, so the outbound list and the inbound rules stay aligned. The source will be at RyanNorouzi/synchrobuilder (placeholder until the repository is public).

Teammate data is untrusted

The design: anything written on another machine reaches Claude as labelled data, never as an instruction.

Claude Code delivers a hook's additionalContext by wrapping it in a system reminder that is inserted where the hook fired. It does not appear as a chat message in the interface, and Claude Code adds no "untrusted" marker of its own. Everything Synchrobuilder injects that did not come from your machine was typed by a teammate, by a teammate's Claude, or by anyone with push access to the remote. So the labelling is the plugin's job.

Identifiers (handle, device, branch, path, task id, symbol, timestamp) are validated against strict rules or withheld entirely; they are never "cleaned". Free text (task summaries, message bodies, handoff items, board titles) goes through a planned sanitizer on the reader's side, at sync time, because a compromised writer bypasses any writer-side step. The sanitizer strips terminal escapes, control and zero-width characters, neutralizes code fences, headings and role labels such as Human: at the start of a line, defangs URLs, redacts secrets, caps each field, and HTML-escapes the rest. Hooks only concatenate strings that were sanitized earlier, which keeps them inside their time budget.

Every injection is one string with a factual preamble, a begin marker, the entries, and an end marker. Both markers carry a 16-hex nonce generated in the hook process per injection and never stored. Every teammate line starts with two spaces and a pipe, every plugin-generated label with two spaces and an at sign, so no teammate text can start at column 0. The literal marker tokens are replaced if they appear inside a message. A final check confirms exactly one begin and one end marker with the same nonce and no line at column 0; if it fails, the hook prints nothing.

Synchrobuilder teammate data (kind=digest, generated 2026-09-18T07:25:03Z by the synchrobuilder plugin on this machine from its local sync cache).   @entry from=bob kind=message to=me seen=2026-09-18T07:22:40Z

  | (the rest of the message)
=== synchrobuilder:end teammate-data nonce=7f3a9c2e5b1d4e08 ===

The ~ Human: line shows the sanitizer at work: a role label at the start of a teammate's line gets a ~ prefix so it cannot read as a turn marker. Human-visible surfaces (status line, permission reasons, the status command) use fixed templates with validated identifiers, counts and times; the one exception is a task summary in the status line, cut to at most 40 printable ASCII characters. ADR-005 lists the open questions still to test, including the exact reminder text on current Claude Code versions.

How the hooks fit

Six hook events, one Node program, no shell. All planned.

EventMatcherWhat the plugin does
SessionStartallInjects the team digest: who is active, claims that touch your area, messages for you, handoffs since you left. Starts the background worker if none holds the lock.
UserPromptSubmitallDelivers your inbox alongside the prompt, plus a one-line notice to you so you know something arrived.
PreToolUseEdit|Write|NotebookEditCollision check against teammates' claims. Warns by default; teams can opt into ask. At most once per file per 30 minutes. Never blocks.
PostToolUseEdit|Write|NotebookEditPortability guard on the file just edited, and contract change alerts, returned as context in the same turn.
StopallStages the handoff incrementally into a local journal, and relaunches the worker if it died.
SessionEndallMarks the session closed and leaves the final push to the worker. Plugin hooks get 1.5 seconds here, so nothing slow happens in this hook.

Every hook is declared in exec form: "command": "node" with "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/run.mjs", "<verb>"]. Claude Code spawns the executable directly with no shell involved. One entry point dispatches on the verb, and the plugin will ship plain ESM with no dependencies and no build step, so what is in the repository is what runs. The matcher for the two edit hooks is PLAN.md open question 8; edits made through Bash are not covered in v1.

The two hooks that run before an edit and on every prompt have a 50 ms budget; a planned internal watchdog set at 40 ms ends the process with no output if work overruns. A Node hook that reads stdin and one small cache file measured about 20 ms end to end on a macOS laptop (30 runs, p50 20.3 ms, experiment E4 in docs/research/experiments.md). The same experiment series showed all six events firing in exec form in a real headless session on Claude Code 2.1.218, with context from the session start, prompt, pre-edit and post-edit hooks reaching Claude in the same turn (E2), and a missing node producing a visible hook error but never a blocked session (E3). Windows and Linux numbers are unknown until CI runs.

Mute is a local flag file that the guard hook checks first, because the Claude Code docs say there is no way to disable an individual hook. The muted guard still runs and prints nothing.

What it is not

Two things it could be mistaken for, and the project it borrows from.

Synchrobuilder is not Anthropic's Agent Teams and not cross-session messaging. Agent Teams is one person orchestrating several Claude Code instances on one machine from one lead session; it is experimental, off by default, local to one home directory, and its team config is removed when the session ends. Cross-session messaging lets one person's Claude Code sessions talk to each other, on one machine through files and a per-user socket or named pipe, and between machines through Anthropic's servers over a Remote Control connection tied to a single claude.ai sign-in. Synchrobuilder is designed for several people, each with their own Claude Code and their own account or provider, on their own machines, sharing durable state that outlives every session, through a remote they already have, with no Anthropic-side relay. The two can coexist. One convention is reused: an incoming message is framed as coming from another session, not from the user, which is the model for the wrapper above.

The closest prior art is claude-code-relay (MIT). Synchrobuilder takes the shape of its client with credit: hooks that read only a local snapshot, a local journal of session events, an outbox that survives being offline, a background worker that does all network work, advisory collisions with a staleness ladder, and a 140-character derived objective. It replaces Relay's hosted hub with the git remote, its /bin/sh wrapper with exec-form Node, and its bundled TypeScript with plain source, and it sends neither reply prose nor diff hunks. No code is copied; if that changes, the MIT notice and a credit line go in the file header.
